## 2. 迁移判定点（做完 B 线之后才启动）

只在 B 线完成后评估，评估材料不是"挑几个样本试试"，而是**三个仓库对齐后的全量差异**。

### 为什么不能靠"挑样本"

我先前用「自设 + 望」当困难样本，那是错的：挑样本本身就是穷举式特殊处理的思路，而且没有对照上游。迁移难度不取决于本项目某个 kit 写得多长，而取决于**本项目相对 AUE 实际运行的那份内容改了多少**。所以判定依据只能是全量比对，样本只是从比对结果里自然浮现的。

### 三方对齐（全部固定提交，不自己挑版本）

| 仓库 | 用途 | 固定点 |
|---|---|---|
| 本项目 | `server/sim/content/kits/ops/` 213 份 | 当前工作区 |
| AUE | 决定**实际跑哪些** kit（`packages/content/data/kits.json` 的 `enabled`） | `b255236`（v0.1.4） |
| Stronghold | kit 源码本体 | `b3deebda`（v0.3.1，AUE 的 kits.json 指定的那个） |

工具：`node tools/report-kit-drift.mjs`（只读）。它把三方对齐后回答三个问题：一致的多少、改过的哪些、缺的哪些。

### 实测结果（2026-10-28）

```
本项目 213 份 kit，覆盖 205 个 charId
AUE 登记 461 名干员，其中 72 名启用专属 kit（Stronghold v0.3.1），其余 389 名靠 AUE 自己的通用实现

对 AUE 启用的那 72 份：
  与本项目完全一致   60 份
  本项目改过         12 份
  本项目没有          0 份
```

玩家可选池共 **205 个槽位**（`AVAILABLE_IDS`），逐个对上是这样：

| 类别 | 数量 | 迁移后的状态 |
|---|---|---|
| 保住专属 kit（AUE 也启用） | 72 | 行为不变或按 12 份的判定处理 |
| **原作干员，本项目有手写 kit，AUE 不启用** | **121** | **改走 AUE 的通用实现** |
| 自设（塔露拉／维娜／结城理） | 3 | 必然自建 |
| 补位干员（Sharp／Stormeye／Touch 等） | 9 | 本项目有 `standin-*.js`，AUE 没有；走通用或自建 |

**先前"133"的说法作废**：那个数字是「本项目有 kit 的 charId 数 − AUE 启用的 charId 数」，其中混进了补位与不在可选池里的条目，没有业务含义。有业务含义的是上表的 121。

### 这 121 是什么性质的问题（必须说清，不能含糊）

不是"没有实现"，而是**保真度可能下降**：

- AUE 的 389 名靠通用实现，是它自己的正常设计路径，不是残缺；本项目同样有 `server/sim/content/generic.js`（469 行）做兜底。
- 但本项目的 121 名用了 Stronghold 的手写 kit，那是逐技能写死的逻辑；AUE 的通用实现读技能的 blackboard（`atk_scale`、`times`、`max_target` 等）套模板。
- 对"攻击力提升 X%、攻击 N 次"这类技能，两者结果应当接近；对需要专门机制的技能（召唤、位移、特殊触发、状态联动），通用模板覆盖不到。

**这条目前是未测项**：到底差多少，必须拿 AUE 的通用实现对同一名干员逐项比对才能回答。在测出来之前，既不能说"会变差"，也不能说"没影响"。

### 判定依据（按重要性）

1. **121 名的保真度落差**——见上，未测，是判定的第一未知量。
2. **12 份改过的 kit** 是否需要保留项目特有行为（详见下表）。
3. **三名自设必然自建**，属固定成本。
4. **净收益**：AUE 登记 461 名，比本项目可选池的 205 多出 256 名，其中多数靠通用实现。

- 改动的原因若已在上游后续版本修复 → 直接用上游版；

### 判定规则

按顺序回答三个问题，任何一个答"不可接受"就停止：

1. **121 名的保真度落差能不能接受？**（未测，见本节开头。这是第一未知量。）
2. **12 份改过的 kit 走哪条路？** 若多数属于"上游后来修好了"→ 走路线 A，成本低；若多数属于"项目特有需求"→ 要在适配层建覆盖层（路线 B），成本中等；若必须在 kit 源码里改 → 停止迁移（路线 C 禁用）。
3. **三名自设 + 9 名补位怎么办？** 自设必然自建，是固定成本；补位要单独定。

两条方法论上的自我提醒，写在这里防止再走回去：

- **不要用"挑几个干员试试"代表迁移难度**——既不代表覆盖面，也没有对照物。判定依据只能是全量比对。
- **不要用"本项目 kit 写了多少行"代表迁移难度**——那只说明本项目自己有多复杂，和「相对 AUE 差多少」是两回事。

## 2.5 接进来之后怎么跟上上游（不打架的前提）

这一节回答一个必须先想清楚的问题：**换了 AUE，以后它更新了怎么办？** 如果答案含糊，接入就等于把项目焊死在一个快照上。

### AUE 官方给的机制就是为这个准备的

上游 ADR 0052 定的是 git 子模块：`engine/` 固定在某个**发布标签对应的提交**上，pnpm 工作区把 `engine/packages/*` 和本项目自己的包一起管；**平台不修改子模块里的任何文件**，要改引擎就在引擎仓库提交、打新标签、再升级。升级动作只有三步：子模块切到新标签 → 提交 → 跑 CI。

这条约定恰好就是我们需要的形态：**上游是只读的，我们的改动永远在它外面。**

### 三层各管各的，冲突面被压到最小

| 层 | 内容 | 上游更新时会不会打架 |
|---|---|---|
| 引擎（`engine/` 子模块） | `@aue/sim`、`@aue/math`、`@aue/schema` 等 | 不打架：我们一行都不改它，升级就是换指向 |
| 适配层（本项目） | 会话桥、关卡文件 → AUE 内容的转换、存档格式转换、结算读数 | 可能打架，但**只有这一处**；它消费的是 AUE 的公开导出，导出签名变了会在启动时立刻报错，不会静默错 |
| 表现层（本项目） | 现有战场视图、`public/js/render/fx/` 的 186 个事件消费端 | 不打架：它只听本项目自己的事件桥，不认识 AUE |

判定标准很直接：**如果某次上游升级需要改动适配层以外的任何东西，就说明上一轮设计漏了一层。** 这是自查用的警报器。

### 真正的冲突点：内容，不是框架

框架层可以做到零冲突，内容层不能。原因在于：那 72 个 kit 不是 AUE 自己的代码，是从 Stronghold Protocol 按固定提交拉来的（`.cache/oracle/`，v0.3.1 / `b3deebda`）。本项目现在也用这些 kit，并且**改过其中一部分**（望、维什戴尔、召唤物手牌、手动部署等）。

于是有三条可选路线，代价递增（12 份的量级让路线 B 变得现实）：

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 全用上游版**（推荐先试） | 本项目改过的 kit 一律让位给 AUE 加载的那份；确有不满就往上流提 | 零冲突，升级无痛；差异表由上游维护 | 本项目的一些修正会暂时丢失，需要逐个确认上游版是否等价 |
| **B. 上游 + 本地覆盖** | 上游 kit 原样不动，本项目另建一份覆盖文件，加载时按 ID 覆写 | 保留修正，升级不打架（覆盖层是我们自己的代码） | 覆盖层要跟着上游的接口变；量大时会变成第二套内容 |
| **C. 直接改 kit 源码** | 把本项目改过的 kit 放回去替换 | 最省事 | **禁用**。这就是"打架"的来源：每次升级都要手工合并 |

12 份改过的 kit 里，望（−50/+13）只是改动量第二大的一个，不是特例；mcnist（−56/+12）改动更多。逐份判断时按前面 §2 的三条规则走，别把任何一份当成"默认要保留"。

### 另外两个会咬人的点

1. **三方版本要一起固定。** AUE 依赖 Stronghold 的固定提交（`kits.json` 的 `source.sha`），Stronghold 又依赖 `Kengxxiao/ArknightsGameData` 的固定提交。三个版本必须成套升级，单独升一个会出现"kit 引用了不存在的字段"。清单里要把三者记成一组，不记单个版本号。
2. **玩家侧的安装方式会变。** 上游要求 `git clone --recurse-submodules` 或 `git submodule update --init`，并且要 pnpm 11.28 + Node ≥ 22.12。本项目现在是"下载 ZIP + 双击 BAT + npm install"，这条路会断。要么在发布阶段预置好 `engine/` 与 kit 源码（做进发行包），要么改掉双击启动链——这是独立的一次改动，不能夹在迁移里顺手做。

### 结论

**接 AUE 不等于焊死。** 前提是三条守得住：子模块只读、我们的改动全在适配层与表现层、内容层走路线 A 或 B 而不是 C。

反过来说，如果对账发现需要走路线 C（直接改 kit），那就该停——那意味着上游的接口撑不住我们的需求，长期会变成每次升级都合并冲突的无底洞。

## 3. C 线：素材索引瘦身（与 B 线并行）

### 3.1 已核实的问题

`tools/assets/plan.mjs:593` 对 `catalog.autochessUi` **全量建叶子，没有任何白名单**：

```js
for (const [group, entries] of Object.entries(catalog?.autochessUi || {})) {
  for (const [key, url] of Object.entries(entries || {})) addUi(group, key, url);
}
```

后果（本机实测）：`public/assets/ui` 落盘 **38.7MB**，其中按文件名扫描未被任何 js/css/html 引用的约 **16.9MB / 515 个文件**。

已确认无人引用的分组（19 组，合计约 4.9MB）：`campLogo`、`modeChoice`、`shopLevelSprite`、`bandChoose`、`shopPanel`、`prepareBkg`、`bondDetail`、`itemRarity`、`eliteLarge`、`bondBoardIcon`、`stageInfo`、`equipSlot`、`chessLevelSprite`、`medalIcon`、`hudBondItem`、`charEliteSprite`、`rarityYellow`、`prepReady`；`hudPanel/bg_board.png` 是用户点名的那张"官方棋盘"——文件在，代码零引用。

另有三个大目录属于**已删除的联机界面遗留**：`settle`（5.4MB）、`loading`（3.6MB）、`entry` 的大部分（2.1MB）。`public/js/screens/` 目录已不存在（`settle.js` 缺失），但 `settle/*` 仍在下载。

### 3.2 做法（已完成白名单与守卫）

路径有动态拼接（`ui['guide/<key>']`、`ui['entry/<key>']`、`ui[\`garrisonTypeIcon/${id}\`]`），盲删会删掉活素材。所以顺序是：

1. ✅ 白名单 `tools/assets/ui-groups.mjs`：`UI_GROUPS`（14 组在用，每组一句用途）+ `LEGACY_GROUPS`（27 组联机遗留，刻意不再下载）。

## 4. 不做：通用干员制作器

结论：**不做"填表就能造干员"的通用制作器。**

理由（都是本项目已确认的事实）：

- 干员的成本不在数值，在机制。现有 3 名自设（塔露拉、维娜、结城理）各自带着专属 kit、专属特效事件与专属状态；结城理还要三套技能运行时。这些不是表格能表达的。
- 若把机制也做成表格，本质就是再造一套 Stronghold 的 kit API（钩子总线、定时器、Buff 规则、事件上下文）。那已经有人做完了。
- 外观更卡死：AUE 的数据 mod 明确**不能**新增敌人、召唤物、攻击范围，也不能带自有图片、模型和声音，新干员只能借用官方外观。我们的自设素材是自制图片＋自制特效。
- 参考实现：AUE 的 `docs/mods.md` 已把"填表"这条路走到了它的上限——改数值、加干员（借外观）、改关卡。那正是"填表可行"的边界，而它不能满足本项目对自设的定义。

替代路径（若将来确有需要）：直接兼容 AUE 的数据 mod 格式，而不是自造一套。这样能白拿它的校验、打包与加载链，且不引入第二种内容格式。
