# 关卡自动复刻设想

**状态：可待实现，很有潜力。** 本文只记录设计与已验证的事实，没有对应代码。

## 要解决的问题

现在复刻一关（例：ISW-NO 圆石技艺）的流程是「读官方关卡 JSON → 手工推断波次规则 → 手算数值倍率 → 逐条填进编辑器」。这关本身消耗了小半天，而其中真正需要人判断的部分可能不到两成。关卡 JSON 的结构化程度足以把其余部分自动化。

## 输入从哪来

| 数据 | 来源 | 形态 |
|---|---|---|
| 关卡本体 | 客户端 `zh_CN/gamedata/levels/...`（集成战略在 `obt/roguelike/`） | 结构化 JSON：`mapData.map`、`routes`、`waves[].fragments[].actions`、`predefines`、`runes` |
| 敌人属性 | `enemy_database.json`（已在 `data/gamedata/`） | 每个 enemy 的 `Value[]` 按 level 分级 |
| 关卡情报 | PRTS 页面「敌方情报」表 | 数量区间、地位、级别、基础数值 |
| 关卡说明 | PRTS 页面「情报」段 | 紧急作战的倍率文案、随机成分描述 |
| 机制语义 | PRTS 备注 / tomimi.dev | 那些数据里没有、只能靠文字确认的规则 |

## 可以自动化的部分（约 80%）

1. **地形**：`mapData.map` 是字符矩阵，逐个映射成 `stage.rows` 的合法字形（`r/f/h/X/#/S/E`）；`tilesDisallowToLocate` 补上「不可部署」。要注意矩阵是**自上而下**，而项目行号自下而上，需要翻行。
2. **路线**：`routes`/`extraRoutes` 的检查点是 `[row, col]`，本来就是自下而上，平移到 `rect` 即可。
3. **出生表**：`waves[].fragments[].actions` 全结构化，`preDelay` 累加就是 `at`；`key` 直接是敌人 key。
4. **难度与倍率**：`runes[].blackboard` 里的 `enemy_attribute_mul`（atk/hp/def）就是关卡自带的难度系数，`difficultyMask` 决定哪档生效。紧急作战的 110%/120%/150% 就是这么来的，不用猜。
5. **敌人数量核对**：筛完出生表后，按敌人种类计数，与 PRTS 情报表的数字对照，对不上就报警。
6. **`meta` 的初值**：部署上限来自 `options.characterLimit`，初始费用来自 `initialCost`，COST 上限来自 `maxCost`。

## 必须人工确认的部分（约 20%）

这些是数据里没有直接答案、只能靠人判断的：

- **同名互斥包的真实语义**：`randomSpawnGroupPackKey` 只给 key（如 `up`/`down`、`t1`/`t2`），到底「互斥」还是「同时出」需要推断。馆石技艺那次是靠「三族敌人算出的数量同时命中 PRTS 数字」才反推出来的。
- **整轮难度加成**：N16 的「每进入新区域，攻击力和生命值额外 +25%」属于玩家的整轮进度，不在关卡数据里，无法折算，只能决定「要不要模拟」。
- **随机成分的取舍**：紧急作战里「50% 概率出现 X」这类，是取期望、取上界、还是照抄某个分支，得由作者定。
- **装置的玩法语义**：`predefines.tokenInsts` 只给装置 key 与位置，装置做什么写在 `character_table` 的技能描述里，常需要 PRTS 备注补充。

## 管线形状

```
官方关卡 JSON + enemy_database
        │
        ├─(纯映射)── 地形 / 路线 / 出生表 / runes 倍率 / meta 初值
        │                        ↓
        │              生成「关卡草稿 JSON」
        │                        ↓
        └─(人工)──── 编辑器打开草稿，对照 PRTS 敌方情报核对数量与波次
                                 ↓
                        定稿 → 保存 → 提交（manifest 盖章）
```

关键点：**草稿要有可读的「推断日志」**。生成器不该只吐 JSON，还要说明「我按这几条规则筛掉了哪些 fragment、为什么」，否则人工核对无从下手。

## 一个具体的接口设想

`tools/level-from-official.mjs`：

```
node tools/level-from-official.mjs \
  --level .cache/level_rogue6_3-7.json \
  --difficulty 16 --emergency --weather shsdgo \
  --author <署名> --out "content/levels/<关卡名>.json"
```

参数对应 `runes.difficultyMask` 的档位与隐藏组开关；生成完自动跑 `npm run levels` 校验一次，再打印「与 PRTS 情报的差异」。

## 为什么值得做

- 复刻成本从「半天」降到「十几分钟核对」；
- 规则以代码形式沉淀，下次遇到同类关卡不用重新推断；
- 生成器的「推断规则」本身就是一份可评审的文档——比散落在提交信息里的推导过程可靠。

## 必须先解决的设计问题：不能只为黑流树海写一套

明日方舟有 6 个集成战略主题（`data/gamedata/roguelike_topic_table.json` 的 `topics`），每主题的难度档位、环境、隐藏组都不一样。**如果生成器里出现 `if (topic === 'rogue_6')`，这套管线就只能用一次。**

所以正确形态是「**主题档案（theme profile）+ 通用生成器**」：生成器只认档案里声明的字段，换主题只是换一份档案。

### 主题档案要描述什么

```jsonc
// content/themes/rogue_6.json（设想）
{
  "theme": "rogue_6",                       // = 关卡 meta.theme
  "name": "沉沦者的黑流树海",
  "levelRoot": "zh_CN/gamedata/levels/obt/roguelike/ro6",   // 关卡 JSON 在客户端的位置
  "difficulty": {
    "source": "roguelike_topic_table.details.rogue_6.difficulties",
    "maxGrade": 16,
    // 档位的实际效果：一部分来自 ruleDesc 文案、一部分来自 runes
    "perGrade": { "16": { "note": "每进入一个新区域，攻防+25%（整轮进度，不可折算）" } }
  },
  "runes": {
    // difficultyMask → 语义。这是「紧急作战」真正的来源
    "FOUR_STAR": { "label": "紧急作战", "multipliers": "from runes.enemy_attribute_mul" },
    "NORMAL":    { "label": "普通" }
  },
  "environments": [                          // 天气 / 地脉，对应隐藏组
    { "id": "shsdgo", "label": "黑流地脉", "hiddenGroup": "shsdgo", "enemy": "enemy_2137_shsdgo", "count": 6 }
  ],
  "spawnRules": [
    "hiddenGroup 需在 runes 里启用",
    "同段内 randomSpawnGroupPackKey 互斥，取首个包",
    "同段内 randomSpawnGroupKey 同组只取一条"
  ]
}
```

### 编辑器里对应什么

现在编辑器只有「难度 0–5」这一个粗粒度数字。要支持 tomimi.dev 那种「难度 / debuff / 紧急-普通」的开关，需要把它扩成：

| 编辑器控件 | 绑定到 | 作用 |
|---|---|---|
| 主题 | `meta.theme` | 决定下面几项的候选值从哪来 |
| 难度等级 | `meta.grade`（新增字段） | 选主题内的档位；生成器据此算倍率 |
| 紧急 / 普通 | `meta.emergency`（新增布尔）或由 `meta.tags` 推导 | 对应 `runes.difficultyMask` |
| 环境 | `meta.environments[]`（新增） | 对应隐藏组与额外敌人（如黑流地脉的猎犬proto） |
| 倍率预览 | 只读 | 显示「生命 ×1.5 / 攻击 ×1.1 / 防御 ×1.2」这类折算结果 |

**关键取舍**：这些字段是「生成器的输入」，还是「关卡文件的既有内容」？

- 若只存**折算后的 `mods`**（现状）：关卡自洽，但丢失了「这是 N16 紧急」的语义，改起来要重算。
- 若存**语义 + 折算结果**（推荐）：`meta.grade/emergency/environments` 说明「这关是什么」，`spawns[].mods` 是「折算成什么」。两者不一致时生成器可以重新折算，编辑器也能显示「你手动改过倍率」。

### 分摊到各主题的工作量

真正需要为每个新主题写的，只有**档案文件**（JSON）与**少数主题特有机制**（如果该主题有关卡专属装置或天气）。生成器、编辑器 UI、校验脚本都不动。这也意味着：**第一个主题的档案要写得很啰嗦**（把规则一条条说清），后面几个主题就只是填空。

## 先决条件

1. `data/gamedata/` 里的表要保持可读（已具备）；
2. 需要一份「关卡字符 → 地形」的映射表（`shared/level.js` 的 `TILES` 已有定义）；
3. 最好先做 2–3 关手工复刻，把规则差异摸清再写生成器——只有一关的样本会过拟合。

## 数据来源已验证（2026-10-26，用 PRTS MCP 实测）

管线需要的三类数据，各自的可靠来源都确认过了：

| 需要什么 | 从哪来 | 实测结果 |
|---|---|---|
| **关卡清单（枚举）** | `data/gamedata/roguelike_topic_table.json` 的 `details.<主题>.stages` | 六主题全有：rogue_1 90 关、rogue_2 97、rogue_3 99、rogue_4 127、rogue_5 178、rogue_6 184。每条带 `levelId`（指向客户端关卡 JSON 的路径）与 `name`、`code`（ISW-NO/ISW-DF/ISW-SP）、`isElite`、`isBoss` |
| **几何与波次** | 客户端 `level_*.json` | `mapData.map`（字符矩阵）、`routes`、`waves[].fragments[].actions`、`runes`、`predefines` |
| **数值校核** | `prts_page(action="template")` | **结构化**返回，比页面正文好读得多：`部署上限 / 初始COST / COST上限 / 目标点耐久 / 敌人数量 / 地图大小`，以及 `敌方情报` 的 `敌人N / 数量 / 数量下限 / 级别`（甚至个别敌人带 `攻击力` 覆写） |

两个反直觉的结论，写进设计前提：

1. **`list_stages` 查不到集成战略关卡**（2523 条里全是活动/主线），`search(scope=stages)` 搜 `ISW` 也是 0 条。所以「枚举」必须走客户端数据，不能指望 MCP 的关卡表。
2. **紧急作战的倍率不是全局常量**：rogue_6 圆石技艺是 攻 110% / 防 120% / 血 150%，而 rogue_1 与虫为伴是 攻防 150% / 血 190%。倍率来自各关卡自己的 `runes.enemy_attribute_mul`，**不能按主题写死，更不能全局写死**——这正是「主题档案 + 通用生成器」必须的理由。
